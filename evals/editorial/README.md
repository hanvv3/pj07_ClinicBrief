# 글 품질 비교 실행하기

같은 주제·근거·작성 요청을 변경 전후의 실제 `OpenAIProvider.compose`에 넣어 비교한다. [사례 v2](cases-v2.json)와 [평가 기준](rubric.md)을 먼저 고정하고, 작성 결과를 본 뒤 유리하게 고치지 않는다. 출처 확인 범위는 [sources-v2.md](sources-v2.md)에 남긴다.

첫 12개 실행은 [v1](cases.json)을 사용했다. 이후 AMIE 입력의 90% 분모가 모호한 것을 발견해, 원문에서 100명 대화 완료·98명 분석·88/98(상위 7개)·73/98(상위 3개)를 구분한 v2를 만들었다. 원본 실행은 `run/`, 해당 사례만 다시 확인한 실행은 `amie-source-correction/`에 보존한다. 아래 `run-v2/` 명령은 향후 새 전체 비교용이며, 12개 전체를 v2로 실행했다는 뜻은 아니다.

## 실행 준비

프롬프트나 작성 코드를 바꾸기 **전에** 기존 `brochure/` 폴더를 별도 로컬 경로의 `baseline/brochure/`로 보관한다. 변경 후 코드를 복사해 놓고 변경 전이라고 부르면 비교가 성립하지 않는다. 이번 기준본은 `.local-data/evals/editorial-2026-11-08/baseline/`이다.

프로젝트 루트에서 기존 Python 환경과 이미 설정된 `OPENAI_API_KEY`를 사용한다. 키 원문을 명령 인자, 사례, 보고서 또는 Git에 넣지 않는다. 기존 `.env.local` 또는 환경변수 설정을 읽으며, 키를 새로 발급하는 도구가 아니다.

우선 입력 경로와 호출 계획을 확인한다. 이 명령은 API를 호출하거나 실행 폴더를 만들지 않는다.

```sh
python3 scripts/evaluate_editorial.py \
  --dataset evals/editorial/cases-v2.json \
  --rubric evals/editorial/rubric.md \
  --baseline .local-data/evals/editorial-2026-11-08/baseline \
  --output .local-data/evals/editorial-2026-11-08/run-v2 \
  --max-calls 84 --dry-run
```

## 생성과 평가

다음은 실제 유료 API 호출을 포함한다. 새 비교를 시작할 때는 다른 `--output` 경로를 정한다. 같은 경로는 기존 시도를 이어 읽는 용도다.

```sh
python3 scripts/evaluate_editorial.py \
  --dataset evals/editorial/cases-v2.json \
  --rubric evals/editorial/rubric.md \
  --baseline .local-data/evals/editorial-2026-11-08/baseline \
  --output .local-data/evals/editorial-2026-11-08/run-v2 \
  --phase all --max-calls 84 --workers 2
```

`--phase generate`로 작성까지만 실행한 뒤, 같은 인자에서 `--phase judge`로 평가를 진행할 수도 있다. `--case 사례ID`를 반복하면 일부 사례만 새 실행에서 비교한다. 실행을 시작하면 사례·기준·모델·호출 예산·실행 코드와 복사된 작성 코드가 고정된다. 이를 바꾼 재개는 거절된다.

기본 모델은 서비스의 기존 설정을 따른다. 두 작성 버전에는 같은 모델을 쓰며, `--model`로 명시할 수 있다. 평가 모델도 기본은 같고 `--judge-model`로 별도 지정할 수 있다. 모델을 같게 두고 요청만 분리하는 것은 **이전 작성 대화나 판정을 공유하지 않는 것**이다. 서로 다른 모델 계열의 독립적인 의견이 생기는 것은 아니다.

한 사례에 최대 7회가 필요하다: 두 버전의 작성·기존 검수 4회, 출처에 한정한 사실 평가 1회, A/B 순서를 바꾼 읽기 품질 평가 2회. 12개 사례의 상한은 총 84회이며, 중단되거나 실패한 시도도 호출 예산에 포함한다. 자동 재시도나 좋은 결과가 나올 때까지의 재작성은 없다. 평가 요청의 출력 상한은 2,600토큰이고 작성·검수에는 실제 서비스 설정을 적용한다.

비용은 호출 수만으로 확정할 수 없다. 실제 응답의 토큰 사용량을 기록하며, 응답을 받지 못해 사용량을 모르는 호출은 별도로 표시한다. 실패한 시도를 다시 시험할 필요가 생기면 원인을 기록하고 별도 실행으로 남긴다.

## 결과 읽기

API 호출 없이 보고서만 다시 만들 수 있다.

```sh
python3 scripts/evaluate_editorial.py \
  --output .local-data/evals/editorial-2026-11-08/run-v2 \
  --phase report
```

실행 폴더의 `report.md`와 `summary.json`에 결과가 모인다. `cases/`에는 작성물·검수 결과·평가와 익명 라벨의 대응표, `calls/`에는 요청·응답 원문·사용량·오류 종류가 남는다. 기존 검수가 거절한 초안도 연구용으로 보존하며 서비스에 게시하지 않는다. HTTP 오류의 본문과 인증 헤더는 저장하지 않는다. 이 자료들은 Git에서 제외된 `.local-data/` 안에 두고, 공유할 때는 필요한 공개 자료만 골라 확인한다.

순서를 바꿔도 같은 버전을 선호해야 안정적인 승리다. 순서에 따라 판정이 바뀌거나, 둘 다 부적합하거나, 근거가 부족한 결과는 승리로 계산하지 않는다. 작성·검수·평가 실패도 12개라는 분모에서 빠지지 않는다. 제목·명료성·자연스러움·가치는 각각 1–5점이며 사실 검수와 별도로 읽는다. 보고서의 평균 점수는 확보된 평가만 반영하므로 평가 수와 누락도 함께 본다.

초기 통과 조건은 고정된 12개를 모두 평가하고, 변경본의 중대한 사실 오류가 없으며, 안정적인 승리가 8개 이상이고 명료성·자연스러움 평균이 오르는 것이다. 이 제품 판단 기준은 평가자에게 전달하지 않는다. 미완료나 근거 부족이 있으면 성공을 입증한 것으로 취급하지 않는다.

## 이 비교가 알려주지 않는 것

이번 12개는 사람이 선별한 사례이며 각 사례의 근거는 단일 출처에서 구성했다. 고정된 근거로 글을 쓰는 능력을 비교하므로, 실제 웹에서 새로운 주제를 발견하는 능력이나 여러 출처의 충돌을 해결하는 능력을 검증하지 않는다. 한 번의 소규모 실행으로 통계적 우월성이나 원장·직원의 만족도를 단정할 수도 없다. 아직 사람의 선호로 평가 모델을 보정하지 않았다.

다음에는 실제 독자가 버전 이름을 가린 글을 읽고 읽을 가치·어색한 표현·바로 쓸 수 있는 내용을 짧게 평가한다. 사실 오류나 판단 불가 사례는 출처와 함께 확인하고, 사람과 평가 모델이 갈리는 이유를 남긴다. 그 결과가 쌓이면 다음 평가 기준을 새 버전으로 만들고, 실제 주제 조사 과정도 별도로 비교한다. 원래 실행의 사례·기준·결과는 그대로 보존한다.

## 이번 입력 수정만 다시 확인한 명령

```sh
python3 scripts/evaluate_editorial.py \
  --dataset evals/editorial/cases-v2.json \
  --rubric evals/editorial/rubric.md \
  --baseline .local-data/evals/editorial-2026-11-08/baseline \
  --output .local-data/evals/editorial-2026-11-08/amie-source-correction \
  --case news-amie-feasibility --max-calls 7 --workers 1 \
  --model gpt-6.1-sol --judge-model gpt-6.1-sol
```

근거 요약을 평가자에게 주면 그 요약의 빈틈도 공유한다. 숫자를 사용하는 사례에서는 무엇의 비율인지 원문과 대조하고, 소수 사례라도 원문부터 생성문까지 별도로 확인해 보는 편이 도움이 된다. 재실행으로 원래 점수를 덮거나 입력 오류를 없었던 일로 만들지 않는다.

## 실제 사용자 피드백과 조사 결과 경로

[human-feedback.json](human-feedback.json)은 사용자가 직접 지적한 문체 실패와 원하는 방향을 보존한다. 사용자가 제안한 표현을 사실 검증까지 마친 정답으로 간주하거나, 아직 보지 않은 수정본을 선호했다고 기록하지 않는다.

기존 평가기는 `compose()` 경로만 실행한다. `discover_insights()`가 만든 `ready_to_use` 본문이 좋아졌는지, 실제 웹 조사가 유용한 주제를 고르는지까지 검증한 결과가 아니다. 환자 메시지 연구의 반례를 계기로 조사 결과의 작성·편집·최종 검수 경로를 별도 확인했다. 이 사례는 수정에 사용한 개발 사례이며, 새로운 주제에 대한 성능이나 사용자 만족을 입증하는 평가 표본은 아니다.
