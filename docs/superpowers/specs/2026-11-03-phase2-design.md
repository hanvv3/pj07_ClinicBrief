# Phase 2 working design

User authorized proceeding to the next phase on 2026-11-03 and chose to configure an existing OpenAI API key personally. Never print the key or create a new one. Keep Phase 1 sources and original specifications unchanged.

## Goal and choices

Connect real researched candidates, AI-led or company-text-assisted composition, correction of both audience materials, account ownership and revision-consistent exports. Reuse Python/SQLite and the existing Korean interface and renderer. A distributed backend and hosted deployment are unnecessary for local Phase 2 validation; production hosting hardening belongs to Phase 3. This remains a loopback application until that gate.

OpenAI Responses API with web_search researches public sources; composition and revisions have NO web tools and receive only selected evidence and relevant inputs. Default model gpt-6.1-sol, configurable with OPENAI_MODEL. It replaces the initial gpt-5-mini after the user requested a capability comparison and frozen generation/audit cases plus fresh research showed improvements. See `docs/verification/model-comparison-2026-11-03.md`; this small comparison is not a reliability guarantee. Credentials read from environment or workspace .env.local without logging. Use store:false, finite HTTP timeout, no automatic paid retries. Current docs: https://developers.openai.com/api/docs/guides/tools-web-search and https://developers.openai.com/api/docs/guides/structured-outputs .

Three fixed broad discovery categories (communication, operations, ai-literacy) prevent private company content from entering public search queries. No specialty/demographic segmentation. Research candidates require completed source-body access (open_page or find_in_page on a loaded page with a direct URL) plus matching native citations in web tool metadata, source context, dates with uncertainty, and claim/source links. Search snippets alone do not qualify. Never silently substitute fixtures on live search failure. Prepared examples remain a separate explicit mode.

Company input is pasted plain text only, 6000 characters; no uploads/OCR. User confirms rights/no patient records and external AI processing. Promotional or patient-specific content must be rejected or neutral portions retained with explicit notices. Input is untrusted data, never privileged instructions. A separate no-tools content audit evaluates evidence and boundaries before saving model composition; generated claims are still subject to user review, not guaranteed verified facts.

Local individual accounts use salted password hashes and opaque expiring sessions with HttpOnly/SameSite Strict cookies. Mutations require CSRF tokens after login. SQLite records and files are scoped by authenticated owner; unknown/other owner IDs return 404. Existing Phase 1 unowned drafts remain inaccessible through authenticated routes (no implicit first-user takeover); keep their files intact. No password reset/email verification/cloud exposure in this phase.

Durable jobs store progress/result/error, survive browser reloads, and mark in-flight work interrupted on server restart rather than rerun billable requests. Per owner at most one active job, global at most two workers; 20 submissions/account/day (including failed work), candidate count at most 3, request body 32 KiB, finite provider calls, no automatic retries. Export keeps its existing bounded partial recovery.

## API contract (for UI and backend)

All errors: `{error: Korean message}`. All existing draft routes now require cookie auth and owner checks. Authenticated POST/PATCH/DELETE require `X-CSRF-Token` from session. Cookie sent same-origin by browser.

- `GET /api/session` -> `{user: {id,email}|null, csrf_token: string|null, provider:{configured:boolean,model:string}, limits:{company_chars:6000, revision_chars:1000}, phase:2}`. Never return secrets.
- `POST /api/auth/register` and `/api/auth/login` body `{email,password}` -> session shape and Set-Cookie. Password 12–128 chars; account email used only as identifier, no email sent. `POST /api/auth/logout` -> `{ok:true}` and clears cookie.
- `GET /api/topics` -> `{topics: Topic[]}` (explicit examples).
- `GET /api/research` -> `{topics: Topic[]}` (owner's saved live candidates).
- `POST /api/research` body `{category:'communication'|'operations'|'ai-literacy',request_id}` -> Job, status 202.
- `GET /api/jobs` -> `{jobs: Job[]}` (latest owner jobs), `GET /api/jobs/{id}` -> Job. Job `{id,kind,status:'queued'|'running'|'succeeded'|'failed'|'interrupted',stage,error,result,created_at,updated_at}`. Result for research `{topics:Topic[]}`, for compose/revise `{draft:Draft}`. Poll 1–2 sec; reload uses GET jobs. Failed work retry uses NEW request_id only on explicit user action; do not retry on network uncertainty.
- `POST /api/compose` body `{topic_id,source:'example'|'research',mode:'ai'|'company',company_text:'',input_confirmed:boolean,sender_name,sender_contact,request_id}` -> Job 202. Any model composition requires input_confirmed true for provider-processing disclosure (even AI mode). Example direct prepared-template path remains `POST /api/drafts` and is labeled explicitly.
- `POST /api/drafts/{id}/revise` body `{revision,instructions,request_id,input_confirmed:true}` -> Job 202. Instructions at most 1000 chars. Produces both brochure and notes together, checks evidence, increments revision, invalidates review/artifacts. Stale revisions rejected before paid work and before saving.
- Existing `GET /api/drafts`, GET/PATCH/DELETE draft, POST review/exports, GET download keep Phase 1 shapes; owner is server-derived, never client input. No auth query tokens in links.
- `DELETE /api/research` clears completed saved research (reject while active job). `DELETE /api/jobs/{id}` removes terminal job results (reject active); UI may expose a simple delete history action to avoid retaining private inputs indefinitely.

Topic uses Phase 1 candidate fields but live candidates need no brochure/notes template. Source fields remain `id,title,publisher,url,published_at,checked_at,context`, plus `updated_at` nullable and `verification` where available. Candidate includes claims `{id,text,source_ids}`, `evidence_status`, `evidence_notice`, `research_date`. Broad claims lacking source support fail closed. Evidence dates are not automatic freshness proof.

Draft keeps Phase 1 fields, adds `origin:'example'|'ai'|'company'`, `company_text` (local private source, never sent to search), `input_notice` and optional `quality_notes`. Creation snapshot stores selected topic so future revisions do not depend on changed catalog. Renderer still consumes only public allowlist; never company raw text or internal metadata.

## Python interfaces

Provider (agent owns): `OpenAIProvider(workspace:Path)`; `.configured -> bool`, `.model -> str`; `discover(category:str, progress:callable=None)->dict` returns `{topics:list,usage:dict}`; `compose(topic:dict, company_text:str='', instructions:str='', previous:dict|None=None, progress:callable=None)->dict` returns `{brochure:dict,notes:dict,quality_notes:list,usage:dict}`. Sender values injected server-side, never invented. `ProviderError(message)` safe str; do not leak response bodies or prompts. `.compose` never has web tools. Export `validate_company_text(text)->str` and `validate_composition(result,topic)->None` for integration as needed.

Auth (agent owns): `AuthStore(path:Path)`; `.register(email,password)->dict` user `{id,email}`; `.login(email,password)->dict` user; `.new_session(user_id)->dict` `{token,csrf_token,user}`; `.session(token)->dict|None` `{csrf_token,user}`; `.logout(token)->None`. `AuthError(message,status=400)` safe. DB independent auth.sqlite3. No dependency on service.py.

Jobs (agent owns): `JobRunner(path:Path,max_workers=2,daily_limit=20)`; `.submit(owner:str,kind:str,request_id:str,payload:dict,work:callable)->dict`; work called `work(progress)`; progress called with Korean stage string; `.get(owner,id)->dict`; `.list(owner)->list`; `.delete(owner,id)->None`; `.active(owner)->bool`; `.shutdown()->None`. Persist only a SHA256 payload signature plus result/errors, not request payload or secrets. Atomic unique(owner,kind,request_id), reject mismatched reuses, owner quotas, failed/interrupted require explicit new key. `JobError(message,status=400)` safe. Output strips owner/signature. DB independent jobs.sqlite3.

Parent owns service/storage/server integration and tests, provider and auth/jobs are independent implementations. UI owns web files and UI harness. Tests use injectable fake providers and real ownership, not fake claims of live validation. Actual provider smoke test only after user configures existing key.

## Validated implementation decisions (2026-11-03)

Discovery uses three bounded requests: a cited public report, strict no-tools candidate extraction, and a separate no-tools candidate audit. The first request permits at most six web actions. If it cites URLs but supplies no matching body-access record, one additional source-reading request may inspect one deterministic cited URL with at most two web actions. Thus discovery uses three requests normally, four at most, and at most eight web actions. There is no request-retry loop. Dedicated reading rejects new searches and any opened/found/cited URL outside its selected URL; downstream extraction then uses only that reading report.

Eligible sources require a completed `open_page`, or a completed `find_in_page` with nonempty pattern and direct HTTPS URL, plus native citation of the same URL. Search results/snippets do not qualify. OpenAI's primary API reference defines page-find as searching within a loaded page; this is a body-access trace, not a guarantee of complete reading or factual accuracy. Sources receive `verification: body_access_and_cited`. Server-assigned S IDs, URL enums, exact ID–URL pairing, membership, and date validation remain mandatory. Facts from a linked PDF cannot be reassigned to its parent landing page. A single strong candidate is preferable to unsupported additions.

The candidate audit is instructed to check all fields, including practical value, source context, nonclinical adaptations and date labels; a failed audit flag rejects the submitted set. It is not proof of factual correctness: live review caught a payment example absent from the original source and an overstated immediate-use label despite passing flags. Before audit/storage, deterministic normalization clears an updated date when its preserved context explicitly identifies that same date only as reviewed. It never invents dates or changes uncertain contexts. Server research/check dates are snapshotted in Asia/Seoul and supplied as trusted application metadata; generated report dates cannot override them. Reading minutes are disclosed editorial estimates, not source-derived claims. Source publication/update dates still require evidence. A representative must review the returned candidates and final material against the original source.

Observed live responses motivated the separation: web+structured output returned malformed IDs/dates and no native citations; a later candidate added unsupported cost benefits; another audit mistook editorial reading time and timezone differences for factual errors. These are observations, not claims of an officially documented API incompatibility. Composition now constrains citation IDs and forbids unsupported causal benefits, with a separate audit.

The dedicated revision request controls permitted presentation changes and subject narrowing; it cannot override evidence or safety rules. It is distinguished from instructions embedded in untrusted source/company material. Neutral company scope/examples can shape clearly labeled editorial suggestions without becoming verified facts. Public prose must be standalone Korean and cannot refer to private quality notes. Known internal field/status names are rejected locally before audit/storage; this addresses an observed company-composition leak, not a guarantee that every inappropriate phrase can be recognized mechanically.

After the frozen model comparison, an additional local check rejects a private opening script copied verbatim into any public prose field (whitespace normalized, at least 24 non-whitespace characters). This avoids false rejection of shared short greetings. It does not detect paraphrases; semantic audience review remains necessary. This validation change did not alter the compared prompts or schemas.

Revision and composition mutable preconditions run only for new jobs after matching request identity. Prepared and generated drafts use disjoint request namespaces and check signatures. Known safe errors retain actionable messages; unknown exceptions stay redacted. Deletion holds the same admission lock across the idle check and removal of saved data/job snapshots; deleted research cannot be selected by a delayed admission. Legacy source dates remain neutrally labeled as displayed dates; explicitly separate publication/update fields retain separate export labels.

Primary guidance: [web search output and citations](https://developers.openai.com/api/docs/guides/tools-web-search#output-and-citations), [Response action definitions](https://developers.openai.com/api/reference/resources/responses/methods/create), [structured output handling mistakes](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes).
