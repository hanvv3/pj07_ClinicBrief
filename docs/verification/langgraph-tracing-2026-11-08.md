# LangGraph와 조사 기록 검증 — 2026-11-08

공개 조사 실행을 실제 LangGraph StateGraph로 옮겼다. 오케스트레이터 아래 두 조사 에이전트가 병렬로 실행되고, 둘이 끝난 뒤 선정·근거 확인·작성·편집·검수로 이어진다. 독립 코드 검토 후 오류 분류·기록 저장 실패·클라우드 조회 지연을 보완했다.

## 확인한 결과

- 전체 Python 테스트 **222개 통과**(17.603초). UI 회귀 검사, JavaScript 구문 검사, `git diff --check` 통과.
- 실제 LangGraph에 barrier를 둔 검사로 두 조사 호출의 중첩 실행과 합류 이후의 선정 실행을 확인했다. 완료 순서가 바뀌어도 출처 연결이 유지되고 서로 다른 작업의 기록이 섞이지 않는다.
- 각 0.2초의 모의 조사 두 건은 약 0.213초에 끝났다. 순차 지연 합계 0.4초와 비교한 실행 구조 검증이며, 실제 웹 조사 전체의 속도 향상 수치는 아니다.
- 성공한 7단계와 HTTP 429로 실패한 3단계를 별도 테스트 계정의 실제 브라우저에서 열었다. 검색 주소·편집 결과를 펼치고, 실패 원인과 제목으로의 초점 이동을 확인했다. 테스트 서버는 종료했고 사용자 DB에 예제를 추가하지 않았다.
- 개인 기록의 소유권, 익명 조회 차단, 공유 수집 기록의 접근 범위, 삭제 연동, GET 조회가 새 작업을 만들지 않는 동작을 검사했다.
- MCP 클라이언트가 실제 stdio 프로토콜로 도구를 발견하고 기록 조회·비교를 실행했다. DB는 읽기 전용이고 경로를 입력받지 않으며 쓰기·삭제·재실행 도구가 없다. 프로젝트의 로컬 Codex 설정 등록도 CLI로 확인했다.
- 사용자가 설정한 LangSmith 키로 **클라우드 전송과 재조회까지 성공**했다. 실제 그래프에 모의 모델을 연결한 검증 실행에서 로컬 호출 7개와 원격 하위 실행 7개가 일치했다. 검증 실행은 `mock-model-no-paid-call` 태그와 제목으로 구분하고, 가짜 토큰 사용량을 전송하지 않았다. 이번 검증에는 유료 모델 호출이 없다.
- 활성 작업 0개를 확인하고 기존 앱을 종료한 뒤 `http://127.0.0.1:8765/`에서 새 코드를 실행했다. 기존 계정·자료·작업 데이터는 유지했다.

## 검증 중 수정한 문제

- 조사 결과가 만들어졌어도 추적 DB 쓰기 실패 때문에 작업 전체가 실패하던 문제: 생성 결과를 보존하고 기록 누락 안내를 남긴다.
- 배열·키가 긴 응답에서 길이 제한을 우회하던 문제: 직렬화한 UTF-8 바이트 기준으로 제한한다. 비교용 해시는 생략 전 전체 입력을 기준으로 계산한다.
- HTTP 오류가 전체 기록에서는 검수 실패로 보이던 문제: 실제 전달된 예외에 안전한 오류 코드를 연결한다. 병렬 조사에서 401과 429가 모두 발생해도 다른 호출의 오류로 바뀌지 않는다.
- 클라우드 전송 직후 기록이 아직 조회되지 않는 문제: NotFound일 때만 최대 세 번 더 조회한다. 대기 합계는 2.5초이며 각 통신 제한은 별도다. 끝까지 보이지 않으면 전송 실패로 단정하지 않고 `unverified`로 남긴다.
- LangSmith 사용량은 공식 `usage_metadata`에 넣으며, 키·헤더·HTTP 오류 원문·모델 내부 reasoning은 내보내지 않는다.

## 증거와 범위

검증 화면은 로컬 `.local-data/langgraph-qa/trace-view.jpg`, 클라우드 확인 결과와 실행 링크는 `.local-data/langgraph-qa/cloud-verification.json`에 있다. 테스트 계정·작업별 기록과 클라우드 워크스페이스 식별자는 Git에 추가하지 않는다.

이번 검증은 실행·관찰·권한·실패 처리에 관한 것이다. 새 주제의 유용성이나 문체 향상을 입증하는 콘텐츠 평가는 하지 않았다. 실제 웹 조사 시간은 앞으로 남는 실행 기록으로 비교할 수 있다. 사용법은 [조사 실행과 기록 확인](../langgraph-tracing.md)에 정리했다.
